## 1. 要解决的三件事（其实是同一个地方）

### (a) 每一间社团开出来的收据都叫 `MIN-2026-0001`

`src/app/money/actions.ts:79`：

```ts
const PREFIX = "MIN";
```

硬写死，没有任何设定。所以 Pertubuhan Seri Harmoni 的收据、和隔壁庙的收据，
号码长得一模一样，而且开头是**你的产品缩写**，不是他们的字号。

社团的收据是给稽核师和 JPPM 看的法定凭证。上面印着别人的商标缩写，
在会员大会上会被问，而且**问的人是对的**。

### (b) 没办法从既有的纸本号码接下去 —— 这挡住每一个真实客户

`allocateReceiptNos()` 永远从 `seq = 1` 开始。

但**任何一间已经在运作的社团，今年都已经开过纸本收据了**。
一间庙 6 月找上你，纸本已经开到第 846 张 —— 用了 Minit 就从 `0001` 重来，
同一个年度、同一个组织、**两套并行的号码**。稽核直接不过，而且这是他们
**第一天就会撞到**的问题，不是边缘案例。

这不是「以後要做的功能」，这是**上线阻挡项**。

### (c) 号码是在应用层算的 —— 有 1000 张天花板，也有竞态

```ts
const { data: existingRows } = await supabase
  .from("receipts").select("receipt_no").eq("org_id", active.id);   // 没有 limit
```

细节见 `docs/审计-2026-08-03-补充发现.md` 第 2 条。摘要：
Supabase 预设 `db-max-rows = 1000` → 静默截断 → `findSequenceGaps` 看到假断号 →
**财政从此永远开不了收据，而且错误讯息只写「失败，请重试」。**

程式码自己的注解也承认了竞态：「a concurrent issuer can win the race once」。

**这三件事都指向同一个结论：号码不该在 TypeScript 里算，该由资料库发。**

## 2. 两个方案

### 方案 A — 最小改动（不建议单独做）

只加 `orgs.receipt_prefix` 和 `orgs.receipt_opening_seq`，
`allocateReceiptNos` 继续在 TS 里算，只是把 `.limit()` 和年份筛选补上。

- ✅ 快，半天
- ✅ 解掉 (a) (b)
- ❌ (c) 的竞态还在；「读 → 算 → 写」中间那个窗口还在
- ❌ 明年还要再回来改一次

### 方案 B — 一次做对（建议）

加两个栏位，**并且把「开收据」整件事收进一个资料库函式**，
在**同一个交易**里完成「配号 → 插捐款 → 插收据 → 回填 receipt_id」。

- ✅ 三件事一次解决
- ✅ 顺便解掉你 P0-2 的 6b（重复开收据）—— 撞到 `(org_id, client_id)` 唯一约束时，
  **回传那张已经开好的收据号码**，而不是「失败，请重试」
- ✅ `money/actions.ts` 从 230 行的四段式补偿逻辑，变成一次 RPC 呼叫
- ⚠️ 要写测试；要 J 手贴 migration
- ⚠️ 中风险 —— 动到钱。所以要**先在 staging 跑**（这也是我建议开第二个免费 Supabase 专案的原因）

**我建议 B。** 理由：(c) 那个 1000 张天花板会在**试点最忙的那个月**爆掉，
而方案 A 留着它。而且 B 让 `money/actions.ts` 变短、变好懂，不是变复杂。

## 3. 方案 B 的设计

### 3.1 `orgs` 加两个栏位

| 栏位 | 型别 | 说明 |
|---|---|---|
| `receipt_prefix` | `text not null default 'MIN'` | 社团自己的字号。`^[A-Z][A-Z0-9]{1,7}$`（1–8 码，大写开头） |
| `receipt_opening_seq` | `integer not null default 0` | **纸本已经开到第几号**。Minit 从 `opening + 1` 开始 |

`receipt_opening_seq` 的语意刻意定成「已经用掉的最後一号」而不是「起始号」——
因为财政心里想的是「我开到 846」，不是「我要从 847 开始」。
少一次心算，少一个 off-by-one。

**两个栏位在开出第一张收据之後就锁死**（trigger）。
理由跟收据身分不可改是同一条：号码序列的定义中途变了，
前後的收据就对不起来，而这是法定凭证。要改只能等下一个年度、或走 `minit_admin`。

> ⚠️ 这两个栏位要不要一起进 `20260728` 那个「特权栏位锁」的清单？
> **我认为要，但用不同的规则**：`extra_credits` 是「永远只有 service role 能动」，
> 这两个是「**第一张收据开出来之前** hq_admin 可以自己设，之後任何人都不能动」。
> 因为它必须让社团在 onboarding 时自己填 —— 那正是这个功能的意义。

### 3.2 一个资料库函式取代四段式

```
public.issue_receipts(p_org_id bigint, p_rows jsonb) returns jsonb
```

在**一个交易**里做完：

1. `pg_advisory_xact_lock(...)` —— 以 org 为单位序列化，同一间社团同时只有一个人在配号
2. 从 `receipts` 用 SQL 算出目前最大序号（**在资料库里 aggregate，没有 1000 列的问题**）
3. 若序列有断号 → `raise exception`，**带上断在哪几号**（现在只回一个 `failed`）
4. 插 `donations`（带 `client_id`、`source`）→ 撞到 `(org_id, client_id)` 唯一约束就
   **取回既有那一列**，不重开
5. 插 `receipts`，回填 `donations.receipt_id`
6. 回传 `{ client_id: receipt_no }`

任何一步失败 → 整个交易回滚 → **不会有「捐款进去了但收据没开」的中间状态**，
也就不再需要 `rollbackDonations()` 和 `needs_reconciliation` 那整套补偿逻辑。

**为什么用 advisory lock 而不是计数器表**：
计数器表更快，但**失败会烧掉号码**（配了没用 = 断号）。
`CLAUDE.md` 规则 2 要求「连号、不可改、**无断号**」，所以要能从实际的 `receipts` 重新推导。
advisory lock 让「读最大值 → 写」变成原子的，同时保留 gap-free。
社团规模的并发（一次几个人在开收据）用这个绰绰有余。

### 3.3 `money/actions.ts` 变成

```ts
const { data, error } = await supabase.rpc("issue_receipts", {
  p_org_id: active.id,
  p_rows: rows,           // 含 clientId / source
});
```

四段式补偿逻辑整段删掉。`IssueResult` 的 `needs_reconciliation` 保留但几乎不会再触发
（只剩「RPC 回来了但网路断在回程」这一种，而那一种**重试是安全的** —— `client_id` 挡住重复）。

### 3.4 UI 要加的（很小）

**建立组织的表单**多两格：

> **收据字号** ` [ PSH ]`　例：PSH-2026-0001
> **纸本已经开到第几号？** ` [ 846 ]`　没有纸本就填 0

配一句白话说明：

> 「我们会从 **PSH-2026-0847** 开始，接着您的收据簿继续。
> 开出第一张之後这两栏就不能改了 —— 号码是法定凭证。」

`/settings` 也显示同样两格，**开过收据之後变成唯读**，旁边写为什么。

## 5. 还需要你决定的三件事

1. **字号谁来定？** 让社团自己填（自由度高，但会有人填 `ABC`），
   还是从 PPM 号码推导（一致，但不像他们自己的字号）？
   **我建议自己填 + 一句说明**：「用您收据簿上已经在用的字号」。
2. **跨年怎么办？** 现在 `MIN-2026-0001` 每年重新从 1 开始。
   多数社团确实是年度归零 —— 但有些是**永续连号**。
   要不要加一个 `receipt_reset_yearly boolean default true`？
   （我建议**先不要**，等有社团要求再说。多一个开关多一种错。）
3. **分会怎么算？** 20 间庙的网络，每一间分会是自己一套号码，还是共用总部的？
   **这个必须现在决定** —— 影响 `issue_receipts` 是用 `org_id` 还是 `root_org_id` 配号，
   改起来很痛。我猜是「每间分会自己一套」（各自有自己的收据簿），但这是你的领域知识。
