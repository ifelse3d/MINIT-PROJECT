## 1. 换电脑完整步骤（写给完全不懂的人）

### 在旧电脑（现在这台）做的事

**第 1 步：把工作存到 GitHub**

双击 `push-to-github.bat`

看到 **「SIAP / DONE」** 才算成功。看到 **「GAGAL / PUSH FAILED」** 就照窗口里的指示做，**不要关掉、不要删任何东西**。

**第 2 步：把钥匙文件抄出来**

有一个文件叫 `.env.local`（在 `C:\dev\minit` 里面）。它装着 AI 和资料库的密码，**故意不进 GitHub**（这是对的，密码不能上传到网上）。

所以要手动带走。安全的方法：

- 用 USB 随身碟拷贝，或者
- 存进密码管理器（1Password、Bitwarden 之类），或者
- **最安全：不要带，到新电脑重新申请一次金钥**（Gemini 的金钥在 Google AI Studio 可以随时重新产生；Supabase 的金钥在 Supabase Dashboard → Project Settings → API 看得到）

⚠️ **绝对不要**把 `.env.local` 的内容贴进聊天、email、WhatsApp 或任何云端笔记。

**第 3 步：记住这件事会发生**

新电脑打开 Minit 的时候，**捐款登记册会是空的**，但收据还在。这不是坏掉了。原因看第 4 节的 P1-2：有一部分资料目前只存在浏览器里，不在云端。这正是要修的问题之一。

### 在新电脑做的事

**第 1 步：装三样东西**（各自去官网下载，一路按「下一步」）


第一次 `git clone` 会跳出窗口叫你登入 GitHub，登入就好。

**第 3 步：放回钥匙文件**

把 `.env.local` 放进 `C:\dev\minit\`（第 2 步抄出来的那个），或者按 `.env.example` 的格式重新填一份新申请的金钥。

打不开的话，去 `http://localhost:3000/health`，那一页会告诉你缺什么。

**第 5 步：以后每天的习惯**

| 时机 | 做什么 |
|---|---|
| 开工前 | 双击 `pull-from-github.bat` |
| 收工前 | 双击 `push-to-github.bat` |

就这两个。`pull` 那个如果发现你有还没存的东西，它会停下来叫你先存，**不会覆盖你的工作**。

### 两台电脑都能改吗？

**能，但不要同时改。**

- **资料库（Supabase）在云端** → 两台看到同一份资料，完全不用担心
- **程式码要靠纪律** → 一次只让一台是「活的」

规则很简单：**离开一台之前 push，到另一台开工之前 pull。**

忘了 pull 就开始改 → 会出现 git 冲突，对新手很难处理。所以宁愿多按一次 `pull-from-github.bat`，它很快，而且它会保护你。

## 2. 这次讨论定下来的决定

以下八条是 2026-07-28 ~ 29 讨论的结论。**动手前先读这一节，不要重新发明。**

### D1 — 注册的是「人」，不是「组织」

**决定**：使用者注册 ≠ 自动得到一个组织。

**流程**：

1. 注册完，先给一个**示范组织**（`orgs.is_demo` 这个栏位已经存在，目前只是个标签、没有行为）。可以立刻用假资料试完整流程，不用等人批准、不用先付钱。**真实组织数 = 0。**
2. 要用真实资料 → 「建立我的组织」，必须填**社团名称 + PPM 注册号码**
3. 系统用 PPM 号码比对：**已经有人建过 → 不给建，改成「申请加入」**，通知该组织的 `hq_admin` 批准

**为什么**（这是最重要的理由，不是防刷）：

同一间庙的秘书和财政各自注册 → 各自自动得到一个组织 → **变成两个 org、两本登记册、两套收据号码**。收据号码是连号不可重复的法定凭证，一分裂就毁了，而且很难合回去。这比有人多开几个 org 蹭免费额度严重得多。

用 PPM 号码当唯一键在这个市场特别合理 —— 客户本来就是**有政府注册号码的社团**，这是现成的唯一识别，一般 SaaS 没有这种东西可用。

### D2 — 额度对外显示 %，对内记 token 和成本

**对使用者**：显示百分比进度条（像 Claude、GPT 那样），不显示次数。

**理由**：可以换模型、换供应商、优化 prompt 而**使用者感受不变**。用次数计价的话，成本结构一改就得重新谈。而且大档案自然贵、小档案自然便宜，不用另立规则。

**代价**：「剩 40%」不能告诉庙的财政够不够用到月底。所以要**两层显示**：

- 卖方案的时候用工作量描述：「每月约 20 份会议记录 + 300 张收据」
- 系统里显示 %，旁边配白话估算：「剩 40% · 大约还能处理 6 份会议记录」

**对内**：`ai_usage` 表要加栏位 —— `input_tokens`、`output_tokens`、`model`、`provider`、`cost_micros`。

⚠️ `cost_micros`（成本，整数微分单位）**必须在写入当时就算好存下来**。不同供应商 token 单价不同、而且会调价；只记 token 的话，换一次供应商所有历史数字就失去可比性，毛利算不出来。

### D3 — 大档案：现阶段只做提醒和硬上限，**不做百分比预测**

现在的漏洞：**一张手写笔记照片和一份 60 页章程 PDF，收费完全一样（2 次），但 token 可能差 30 倍以上。** 这不是「可能亏」，是确定亏。

各项难度差很多：

| 要做的事 | 难度 | 准不准 |
|---|---|---|
| 数 PDF 页数、图片张数、位元组数 | **很简单**，不用呼叫 AI | **完全准确**（数出来的） |
| 从页数推 input token | 中等 | 还可以（图片按尺寸切格计价，其实固定） |
| 预测 output token | **难** | **不准** |
| 给 `max_tokens` 封顶 | 很简单 | 最坏情况变已知 |

**所以现阶段只做四件**：

1. 数页数/张数 → 超过上限直接拒绝，建议拆开处理（目前只有 `MAX_BYTES = 8MB` 一个门槛，`src/app/api/intake/route.ts`）
2. 大档案给**白话提醒**，不报数字：「这份 32 页，比一般会议记录大很多，会用掉比较多额度」
3. 每次呼叫都设 `max_tokens`（输出 token 通常比输入贵 3–5 倍，生成失控比读长 PDF 更贵）
4. 长章程改成**分段处理**，一段一段扣，中途可以停

**顺序是：先记录 → 再观察 → 才预测。** 跑一两个月拿到真实 token 资料之后，再做校准过的预测。现在硬做预测一定不准，而**不准的预测比没有预测更糟**（使用者会不信任整个额度系统）。

### D4 — 免费策略：绑帐号的一次性小额试用

- 免费额度给**帐号**，不给 org（否则开一堆 org 就刷爆）
- **一次性**，不是每月给
- 额度给小 —— 够拍一次会议记录 + 开一次收据，看到价值就够
- 注册要验证（手机 或 PPM 号码）
- **免费层不含分会、不含额外成员席位**

⚠️ **收费前的硬门槛**：目前用 Gemini **免费层**。`CLAUDE.md` 明文写着免费层可能拿输入去训练，PDPA 上**只能放假资料**。所以在切到付费 API 之前，不能让任何真实社团上传真实捐款人姓名和身份证号。这不是技术细节，是商业前提。

### D5 — 方案分层

| | 免费试用 | 基本方案 | 分会方案 |
|---|---|---|---|
| 示范组织 | 1 | 1 | 1 |
| 真实 root 组织 | **0**（待确认，见第 5 节） | 1 | 1 |
| 额外 root 组织 | 0 | 0 | 0（另购） |
| 分会 | **0** | **0** | 依方案 N 个 |
| 成员席位 | 1（自己） | 依方案 | 依方案 |
| AI 额度 | 一次性小额 | 每月 % | 每月 %（较高） |

**技术现况**：`parent_org_id` 树状结构、`org_descendants()` 递回查询、HQ 角色自动继承到分会、删除时挡住还有分会的 org —— **全部已经做好了**。缺的只有「这个帐号的方案允不允许建分会」这一个检查。

⚠️ 现在任何人都能建分会。**要先关上**，不然最贵的功能在免费层就送出去了。

### D6 — 额度余额改成只增不改的流水帐

`orgs.extra_credits` 现在是一个可以 UPDATE 的整数 → 被改了查不出是谁、什么时候、改多少。

**改成 ledger（流水帐）**：每一笔加值、消耗、退款各一列，**只增不改**，余额 = 全部加总。

这正是 `CLAUDE.md` 规则 2 对收据的要求（连号、不可改、无断号）。**额度就是钱，套一样的规则。**

### D7 — 管理后台先做「错误与失败追踪」

现在**完全没有**：没有 superadmin 角色、没有 Sentry、没有 analytics，整个 `src/` 只有一个 `console.` 而且在注解里。要给某个社团加额度、批 s.44(6)、加成员，都得手动进 Supabase 跑 SQL。

**先做的**：错误与失败追踪 —— 哪个 org 的哪个功能失败了、AI 回传解析失败、上传失败。

**关键做法（PDPA）**：**记事件，不记内容。** 记「org 12 的 `extract_ledger` 在 zod 验证失败」，**不记**那张照片里有什么。这样既能除错，又不违反规则 5。

**后面才做**：注册与用量总览、手动操作工具（改额度、批税务状态、加成员、停用帐号）、异常侦测（一个帐号连开 5 个 org、某个 org 用量突然 10 倍、同一 IP 注册 20 个帐号）。

### D8 — Migration 用 CLI 管理，schema 先、程式码后

**现况**：`supabase/migrations/` 有 5 个档案，但**没有任何套用纪录**，全靠手贴 SQL —— 所以有两个漏掉了没人发现（见 P0-1、P0-2）。

**Claude 无法连线到 Supabase**（沙盒对外网路是白名单制，实测回传 `000`）。所以套 migration 一定要**你在自己电脑上执行**。两条路：

- **短期**：Claude 写好 SQL，你贴进 Supabase Dashboard → SQL Editor
- **之后**：装 Supabase CLI，Claude 写 migration 档、你跑 `supabase db push`（它会记住哪些套过了）

**铁律**：

> **资料库 migration 必须在程式码部署之前套用。**

现在 `src/app/money/actions.ts` 拒绝写 `client_id`，就是因为程式码先上了、migration 没套。规则：先套 schema、再部署程式码，而且程式码要能容忍「栏位还没有」的状态。

## 3. 安全五条规则

### 规则 1：钱和权限的栏位必须用 trigger 锁死，只有 service role 能动

包括 `extra_credits`、`monthly_free_quota`、`tax_exempt_status`、`parent_org_id`、`role`。

### 规则 2：凡是浏览器可写的栏位，都当成敌意输入

这是 `extra_credits` 漏洞的**真正原因**，不是谁写错一行：

Supabase 的设计是「浏览器拿 anon key 直接打 PostgREST，靠 RLS 挡」。RLS 能挡「哪些**列**」，但**挡不了「哪些栏位」** —— 所以只要允许 `hq_admin` 更新 `orgs`，他就能更新 `orgs` 的**任何**栏位，包括自己的额度。

**UI 上把输入框拿掉完全没用**，devtools 里一行 fetch 就绕过。必须在资料库层挡。

大平台的做法是所有写入都经过自己的 API 层、资料库从不对外。不需要整个改架构，但要记住这条规则。

### 规则 3：配额之外还要加速率限制

**这是两件不同的事**：配额防超支，速率限制防滥用。

现在**没有任何速率限制** —— 有人可以在 3 秒内把 100 次额度打完，或者拿这个服务当免费 AI proxy 把 Gemini 帐单打爆。

Claude 那边是「5 小时 session 额度 + 每周额度」两层叠，就是这个用途。

**加的位置**：`src/proxy.ts`（已经是每个请求都经过的地方）。

### 规则 4：加 idempotency key，防重复扣费

网路不稳时使用者按两下 → 扣两次。收据那边有 `client_id` 已经做了一半（但那个 migration 也没套用），**AI 呼叫这边完全没有**。

### 规则 5：除了 superadmin，所有角色都不可信

现在的模型隐含假设 `hq_admin` 是好人（所以让他改自己的额度）。任何多租户系统的铁律是：**除了自己的 superadmin，其他所有角色都不可信。**

不是说社团的秘书会作恶，而是**「他做不到」比「他不会做」可靠得多**。

**已经做对的一件事**：`checkAndRecordUsage` 在呼叫供应商**之前**扣费，这是正确顺序。反过来（先服务再扣）会被人用断线的方式白吃。

## 4. 已知问题清单（按优先顺序）

### P0 — 安全与金钱，最先修

**P0-1：`extra_credits` 自助充值漏洞** 🔴
任何 `hq_admin` 都能改自己的 AI 额度余额。`src/app/orgs/credit-form.tsx` 有输入框和「保存」，但**就算把 UI 拿掉也没用**，浏览器可以直接 `PATCH /rest/v1/orgs` 改成 999999。

程式码里的注解自己都承认了：
> `// This is a SELF-SERVICE AI-quota grant: the organisation's own admin sets their own credit balance. That defeats the metering layer`

**修法**：套用 `supabase/migrations/20260728000000_lock_org_privileged_columns.sql`（**已写好，标头写着 NOT YET APPLIED**）+ 把 `credit-form.tsx` 改成纯显示。

⚠️ **套之前要先验证**：`refundUsage()`（被礼貌拒绝时把额度加回去）会不会被 trigger 挡掉。它走 service role、理论上有豁免，但之前的审计报告提过这里有 bug。**「拒绝不扣额度」是 `CLAUDE.md` 规则 10 的硬要求，不能弄坏。**

**P0-2：收据号码目前改得动** 🔴
`supabase/migrations/20260726000000_client_id_and_receipt_lock.sql` 也**没套用**，所以收据身分不可修改的 trigger 没生效。对财务凭证是致命的。同时 `donations.client_id` / `source` 栏位不存在，`src/app/money/actions.ts:124-127` 因此拒绝写入。

**P0-3：建立组织没有任何数量上限** 🟠
`src/app/orgs/actions.ts` 的 `createOrg` 没有 count 检查，而每个新 org 自动得到 `monthly_free_quota = 100`（DB 栏位预设值）。开 10 个 org = 每月 1000 次免费 AI。→ 按 D1 + D5 修。

**P0-4：没有速率限制** 🟠
见安全规则 3。

**P0-5：`parent_org_id` 可被自助修改 + 递回查询没有防迴圈** 🔴（2026-07-29 白天发现，已修在 migration 里，尚未套用）
安全规则 1 列了 `parent_org_id`，但 `20260728` 那个 migration 原本只锁三栏、漏了它。
`orgs_update` 这条 RLS 的 `with check` 只验「这列是不是你管的」——改上层时 id 不变，**检查会过**，所以任何 hq_admin 都能从浏览器 `PATCH` 改自己的上层。
真正致命的是第二半：`org_descendants()`（`20260719000000`）是没有 cycle 侦测的 `with recursive ... union all`，而 `accessible_orgs()` / `_writable()` / `_admin()` 全部呼叫它，**等於每一条 RLS 政策都呼叫它**。所以一个「自己是自己的上层」就会让资料库每一次查询无限递回 —— 全站停摆，而且停摆后 UI 读不到任何东西，只能进资料库手救。可以被恶意触发，也可以被误触。
**修法（已写进档案）**：trigger 加锁 `parent_org_id`；`org_descendants()` 换成带路径、拒绝重访节点的版本。两边都要做 —— 锁挡住浏览器，路径版挡住其他管道（service role、逃生门、以后的管理后台、手打的 UPDATE）。
成本零：`src/` 从来没有 UPDATE 过这一栏，trigger 只管 UPDATE，建分会不受影响。

### P1 — 产品目前还不能被团队使用

**P1-1：没有「邀请成员」的功能** 🔴
`members_roles` 表和 RLS 政策**都写好了**（六个角色：`hq_admin` / `committee` / `secretary` / `treasurer` / `collector` / `auditor_readonly`），但**没有任何页面或 API 能新增成员**。唯一的写入是 `createOrg` 帮建立者自己插一列 `hq_admin`。

`/orgs` 页面的空状态甚至写着「叫管理你们组织的人把你加进来」—— 而那个人**没有任何按钮可以按**。

后果：一个社团的秘书和财政**无法在同一个 org 里协作**。这不只是定价问题 —— 「多少钱开给多少人」这个方案现在没有东西可以卖。

（D1 的「申请加入」流程会顺便解决一半：成员可以自己申请，不用纯靠 admin 主动邀请。）

**P1-2：一半的资料只存在浏览器里，不跨装置** 🔴

**存在云端（Supabase）的**：上传的原始照片/PDF（私有 bucket）、已确认的会议记录、已开出的收据、orgs 和角色、AI 用量。

**只存在那台浏览器（localStorage）的**：

| key | 内容 |
|---|---|
| `minit:money:donations:v1` | 整本捐款登记册，**含捐款人全名** |
| `minit:money:batches:v1` | 收款人→总部的托管/缴款批次 |
| `minit.constitution.v1` | 已确认的章程条文（整个问答语料库） |
| `minit.minutes.v1` | 进行中的会议记录，**连那张照片** |
| `minit.events` | 社团日历活动 |

后果：财政在手机、秘书在笔电，**看到两本不同的登记册、不同的托管余额、不同的章程**。谁清一下浏览器就全没了。`/filings` 的 eROSES paste-pack 只在拍照那台机器看得到。

附带两个问题：
- localStorage 满了时 `saveMinutes()` 会**丢掉来源照片**（唯一的稽核证据），只回一个 `"photo-dropped"`
