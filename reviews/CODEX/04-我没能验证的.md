## 二、我由代码推导的（没有在 production 亲手重现）

### 跨帐号／跨组织 localStorage 泄漏链

我确认的事实：

1. 钱、会议、章程、活动使用固定 key：`src/app/money/register-store.tsx:196-210`、`src/app/minutes/minutes-storage.ts:20`、`src/app/constitution/constitution-review.tsx:58-59`、`src/lib/local-events.ts:32`。
2. 登出只调用 Supabase sign-out 与 redirect：`src/components/v2/org-chip.tsx:49-53`。
3. 正式 money／minutes action 重新读取当前 active org，再把 client payload 写到该 org：`src/app/money/actions.ts:81-150`、`src/app/minutes/actions.ts:62,139-165`。

因此「A 留在浏览器的 working copy，切到 B 后仍可见并可能以 B 写入」是强推论，不是我用两个真实帐号做过的 screen recording。若 provider 在 layout unmount 时另有未读到的全面清理机制，这个结论会减弱；全 repo 搜寻没有找到该机制。

### 收据重复／效能

- 当前 action 不写 `client_id` 且以 per-row insert／update 运作，这是直接看到的；「断线后重按产生重复」来自 idempotency 缺失的推论，我没有故意中断生产 request。
- 「200 笔约 400 多次 DB round-trip」按 `src/app/money/actions.ts:131-150,193-201` 的两个 per-row loop 加前后查询估算；没有在目标 Vercel／Supabase region 做 wall-clock benchmark，不能断言一定 timeout。
- migration 中有 `issue_receipts()`，但 `src/` 无 caller 是搜寻结果。它**是否已在当前线上数据库套用**我没有查询；文件 header 与状态文件也存在时间差，所以建议先由 owner 的 migration checker／SQL Editor确认，再接应用。

### MyInvois

- 「当前档不是官方 upload template」来自代码自己的明确注释与 workbook 指示：`src/lib/einvois-xlsx.ts:11-17,47-58`。
- 我没有登入真实 MyInvois portal 上传该档，不能提供 portal rejection screenshot；官方模板、分类码、RM10,000 规则是否仍为 2026-08-24 最新，也没有独立法律／税务验证。

### 68 岁使用者行为

- C 表分数来自画面复杂度、触控尺寸、步骤数量与人工附档要求的推断，不是观察一位 68 岁财政完成任务。因此分数只适合排优先度，不是 usability evidence。

- **51/100** 与「进初赛约 30%」是我在系统优先权重下模拟 MAIC 评审的主观判断；我不知道三位实际评审、正规化分布、其他队伍水准，也没有评审内部资料。slide 能快速修正，所以没有再把它当主要扣分来源。
