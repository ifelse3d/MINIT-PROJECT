# CODEX 外部评审：建议

## 一、7 天内：只做系统

### P0-1 修资料边界，并把开收据接到一个真正的 transaction
- **解决哪一条**：02-01、02-02、02-06
- **动哪些档案**：`src/app/money/register-store.tsx`、`src/app/minutes/minutes-storage.ts`、`src/app/constitution/constitution-review.tsx`、`src/lib/local-events.ts`、`src/components/v2/org-chip.tsx`、`src/app/settings/actions.ts`、`src/app/money/actions.ts`、对应 migration／tests
- **估多久**：**1–1.5 天**，含 multi-account／multi-org test；migration 仍由 J 人手套用
- **不做会怎样**：真人资料可能跨组织显示或被错误盖章；删除承诺不实；断线重按可能重复开收据。
- **更便宜的替代做法**：修完前关闭真实资料输入，只允许 fictional sample；登出／切 org 清空 working copy。正式解法是 key 带 `userId:orgId`、正式资料进 Supabase；开收据完成／套用现有 `issue_receipts()` 后只调用 RPC，不再扩写 rollback loop。

### P0-2 把会议记录做成第一个真正完整的系统流程
- **解决哪一条**：02-05、02-11、02-12
- **动哪些档案**：minutes upload／review／draft actions、`minutes_docs` schema、history／resume page、`committee_roster`／eROSES mapping、对应 tests
- **估多久**：**3–5 天**；真实手写样本另外依赖 J
- **不做会怎样**：现在虽能读、核对、出文，但中断后不能可靠继续，另一位秘书不能接手，真实手写准确率也不知道；这不算完成的系统。
- **更便宜的替代做法**：先只完成 minutes：server-side draft、自动保存、回来继续、确认后锁版本、history 可下载。不要同时补 AGM、calendar、glossary。

### P0-3 把捐款→收据→现金交接做成第二条可审计流程
- **解决哪一条**：02-04、02-06、02-09、02-14
- **动哪些档案**：money actions／RPC、receipt void／reissue、register list、custody actions、MyInvois／WhatsApp copy 与 tests
- **估多久**：**4–6 天**，不含官方 MyInvois API
- **不做会怎样**：钱的流程仍有重复、半成功、大量资料不可操作、附件误导、税务档定位错误；任何一个都足以停止真实 pilot。
- **更便宜的替代做法**：先限制每 batch 50 笔；MyInvois 明叫 pre-fill pack；WhatsApp 明示手动附档；错误收据只能 void＋reissue，号码不删除、不复用。

### P0-4 把系统从「三语展示」改成「一个人选一种主要语言」
- **解决哪一条**：02-13、02-15、02-17
- **动哪些档案**：`src/components/language-provider.tsx`、sidebar、section tabs、page section、login、各 task chrome
- **估多久**：**1–2 天**
- **不做会怎样**：系统功能越多，三语字串越长，老人和手机使用者越难完成任务；这是系统资讯架构问题，不是纯美术。
- **更便宜的替代做法**：首次使用只选 BM／中文／English 其中一项；输出语言另选。拿掉重复 step 数字，顶部触控目标至少 44px。

### P0-5 建立系统 gate：两组织、两帐号、断线、重整、200 笔
- **解决哪一条**：02-01、02-02、02-06、02-11、02-14
- **动哪些档案**：authenticated E2E、fixtures、migration checker、staging seed／cleanup、关键流程 metrics
- **估多久**：**2–3 天**
- **不做会怎样**：648 个 unit tests 继续全绿，但真正的登入、切组织、跨页面保存、断线重试仍可能坏。
- **更便宜的替代做法**：先做 5 条 smoke E2E：A/B org 隔离、登出清理、minutes resume、同一批收据重按只产生一次、200 笔完成时间与 DB 笔数。

### P0-6 每完成一条核心流程，立刻找真人做无教学任务测试
- **解决哪一条**：02-05、02-11、02-13、02-14、02-15
- **动哪些档案**：测试脚本、匿名观察纪录、由失败案例新增 regression tests
- **估多久**：每轮 **半天**；最低 3 人
- **不做会怎样**：系统会继续按照开发者理解变得「功能完整」，但秘书／财政仍走不完。
- **更便宜的替代做法**：1 位现任秘书、1 位现任财政、1 位 60+ 使用者；给任务不教学，只记完成率、时间、求助、错误。

### 系统开发顺序（不是比赛排程）

| 顺序 | 完成定义 |
|---|---|
| 1 | 不会串 org／account；删除能删完整；正式钱不会因重按重复 |
| 2 | minutes 可上传、核对、自动存草稿、离开、回来继续、确认、看 history |
| 3 | money 可处理 200 笔、开收据可 void／reissue、交接可审计 |
| 4 | MyInvois／WhatsApp／法律页面说的每一句都等于系统实际做到的事 |
| 5 | 3–5 位目标使用者不靠教学完成；失败点有 test |
| 6 | 再接 roster→eROSES、AGM、calendar 等外围功能 |

**不要为了 8/31 把六项都半做。** 若只能选，先做第 1，再把第 2 做完整。slide 等系统稳定后再据实更新，通常只需数小时。

## 二、交件之后、给真实社团用之前

### P1-1 建立完整 data inventory、删除／保留政策和公开注册 gate
- **解决哪一条**：02-01、02-02、02-07、02-08
- **动哪些档案**：所有 localStorage／Storage／DB 写入点、`legal/`、`src/legal/documents.ts`、signup、settings deletion、资料导出
- **估多久**：**3–5 天工程＋独立法律审阅时间**
- **不做会怎样**：不能对资料主体准确说明资料在哪里、谁处理、多久删除；公开注册与收费争议不可控。
- **更便宜的替代做法**：在实体、联系方式、processor region、保留期没有确认前，关闭 self-signup，仅做书面同意的封闭 pilot；不要自称「lawyer reviewed」。

### P1-2 把会议、捐款、交接全部改成 server-owned draft＋history
- **解决哪一条**：02-01、02-06、02-11、02-12
- **动哪些档案**：`minutes_docs` schema／actions、donations／remittance actions、history pages、local working-copy migration
- **估多久**：**4–7 天**
- **不做会怎样**：两位义工不能接力、换手机即丢、确认与草稿没有清楚责任线。
- **更便宜的替代做法**：先只给会议记录做 draft／resume／version；钱的 working copy在离开页面前强制保存，不做全功能 offline sync。

### P1-3 由真实业务专家逐栏验证 eROSES 与 MyInvois
- **解决哪一条**：02-04、02-12
- **动哪些档案**：`src/lib/eroses.ts`、`src/lib/einvois.ts`、`src/lib/einvois-xlsx.ts`、输出模板、mapping tests、用户说明
- **估多久**：**1–3 天工程＋外部专家／portal 时间**
- **不做会怎样**：系统会非常顺畅地产生不能交的文件，这是 compliance 产品最坏的失败。
- **更便宜的替代做法**：MyInvois 永远叫「pre-fill copy pack」并逐步显示官方 template 的人工动作；eROSES 只输出「建议贴上内容」，不叫 ready／compliant。

### P1-4 补齐正式收据生命周期和大量资料操作
- **解决哪一条**：02-06、02-09、02-14
- **动哪些档案**：receipt schema／RPC、void／reissue audit、register list、bulk operations、200-row performance test
- **估多久**：**3–5 天**
- **不做会怎样**：号码打错、捐款取消、断线重试和大量节庆捐款没有可审计补救。
- **更便宜的替代做法**：上线前限制每 batch 50 笔；错误只能「作废并引用原号码」，绝不删除／复用号码。

### P1-5 做 authenticated E2E 与部署后可观测性
- **解决哪一条**：02-06、02-10、02-11
- **动哪些档案**：Playwright test、test fixtures、Vercel health／error logging、关键流程 metrics、backup restore runbook
- **估多久**：**3–4 天**
- **不做会怎样**：648 个 unit tests 仍无法告诉你登入、切 org、上传、重整、断线、PDF 下载和权限串起来有没有坏。
- **更便宜的替代做法**：先做 5 条 smoke E2E：注册／登入、切 org 隔离、手写会议到保存、200 笔幂等开收据、删除后 client/server 都无资料。

### P1-6 接通真实 roster，暂时隐藏全示范 AGM pack
- **解决哪一条**：02-12
- **动哪些档案**：`committee_roster` 查询、eROSES mapping、AGM inputs／exports、navigation／deck
- **估多久**：**2–4 天**
- **不做会怎样**：同一个组织在不同文件出现不同理事名单，使用者把 SAMPLE 当真档。
- **更便宜的替代做法**：在 roster 接通前，从默认导航和比赛 deck 移除 AGM pack；保留内部实验页。

## 三、之后

### P2-1 用一个真实网络做 6–8 周窄 pilot，再决定价格和目标客户
- **解决哪一条**：02-16
- **动哪些档案**：商业模型、onboarding、support runbook、usage／cost dashboard
- **估多久**：**6–8 周**
- **不做会怎样**：RM39／99／188 只是 spreadsheet 选择，无法知道卖给单一社团还是 HQ network。
- **更便宜的替代做法**：先只卖「会议记录＋eROSES paste pack」或「捐款＋收据」其中一条，按月人工 invoicing；记录每 org 支援分钟数与 AI 成本。

### P2-2 有真实瓶颈后才加 queue／background jobs；不要换技术栈
- **解决哪一条**：02-06、02-14
- **动哪些档案**：长文件处理、job state、retry／idempotency、metrics；必要时才加 queue provider
- **估多久**：**1–2 周**
- **不做会怎样**：若真实文件处理超过 request limit，会 timeout；但现在提前改微服务只会吃掉验证产品的时间。
- **更便宜的替代做法**：保留 Next.js＋Supabase。它们不是当前失败原因；当前问题是资料边界、事实一致性和证据。先限制页数／batch size，并显示可恢复状态。

### P2-3 只有客户愿意付费时才做官方 WhatsApp／MyInvois API
- **解决哪一条**：02-04、02-09
- **动哪些档案**：provider integration、credentials／consent、delivery status、webhook、audit
- **估多久**：WhatsApp **1–2 周**；MyInvois API **2 周以上**且需凭证／合规验证
- **不做会怎样**：长期体验仍有人工附档／上传；但这不是 7 天该冒的整合风险。
- **更便宜的替代做法**：保留官方 `wa.me`，把两步写老实；MyInvois 保留 verified pre-fill。绝对不要用非官方 WhatsApp automation。

## 三个必须回答的问题

### 如果只能做一件事

**把「会议记录」这一条垂直流程做到 production-ready。** 完成定义是：真实手写输入 → 逐栏来源／信心／missing → 人修正 → server-side 自动存草稿 → 退出后回来继续 → 确认后锁版本与审计行 → history 可找回／下载；全程按 user/org 隔离。不是影片，也不是多加一个页面，而是一条真人可以独立完成、不会丢、不会串组织的系统流程。

钱的跨组织 working copy 是上线红线；在它修好前不要放真实捐款资料。若当前只开发会议流程，也要共用同一套 tenant-scoped draft 设计，不能再加一个 fixed localStorage key。

### 如果必须砍掉一个功能

**从系统默认导航砍掉 AGM pack。** `src/app/agm-pack/agm-pack-review.tsx:133-138` 自己承认整页仍是 invented sample；它没有接真实 roster，却占导航、测试和使用者心智。不是删代码，先隐藏，等 canonical roster 接通再回来。不要砍会议或捐款，两者才是产品的楔子。

### 产品最强的一点

**「AI 读、普通代码算、每个事实有来源、人确认后才成为正式记录」这一条架构原则。** 这比泛用聊天机器人有明确责任边界，也适合高后果的社团合规。真正的 moat 目前不是 648 tests 或多模型 provider，而是能否把这条原则在真实混合语言手写材料上证明、持续量化。方向强，证据还没跟上。
