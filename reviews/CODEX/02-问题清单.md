## 逐条证据

### 01. 同一台装置会把 A 组织／帐号的敏感资料留给 B，并可能以 B 的名义存出正式记录
- **严重度**：🔴 挡住上线
- **在哪**：`src/app/money/register-store.tsx:196-210`、`src/app/minutes/minutes-storage.ts:20,45-59`、`src/app/constitution/constitution-review.tsx:58-59`、`src/lib/local-events.ts:32-46`、`src/components/v2/org-chip.tsx:49-53`、`src/app/money/actions.ts:81-150`
- **谁会踩到**：都会，特别是共用礼堂电脑／同一人管理总会和分会
- **会发生什么**：这些 key 都不含 user id 或 org id；切组织或登出再登入后，浏览器 working copy 仍在。钱页随后用「当前 active org」把旧 donations 存入数据库、开收据；最坏情况是 A 的捐款人姓名、电话、金额出现在 B 的正式收据／税务 pack。会议、章程、活动也会串组织。
- **为什么会变成这样**：推测是系统从单组织、local-first prototype 演进到 multi-org，数据库 RLS 做了隔离，但 browser persistence 没随 tenancy 设计升级。这是本评审找到、原 prompt 没列出的最高风险。

### 02. 删除组织与隐私承诺说「不留副本」，实际不会删这些浏览器资料
- **严重度**：🔴 挡住上线
- **在哪**：`src/app/settings/delete-org-section.tsx:46-50`、`src/app/settings/actions.ts:83-100`、`src/lib/use-persistent-state.ts:44-50`
- **谁会踩到**：真实社团、资料主体、管理员
- **会发生什么**：server action 删 Storage／DB 和 cookie，不可能触及 localStorage；坏掉的 blob 还会被另存成带时间戳的 key。使用者看到的「No copy is kept」是事实错误，也让资料删除请求无法履行。
- **为什么会变成这样**：删除功能只枚举 server-owned data，没有一份完整 data inventory 把 client-owned copies 算进去。

### 03. 参赛资料同时在推两个互相无关的产品，其中一个 demo 已从产品移除
- **严重度**：🟡 不影响系统本体，但挡住交件
- **在哪**：`competition/deck/Minit-Pitch-Deck-CURRENT.pdf:全 10 页`、`competition/r1-draft/01_PROJECT_SUMMARY.txt:全文`、`competition/r1-draft/02_AI_DISCLOSURE.txt:全文`、`competition/r1-draft/06_DEMO_SCRIPT_3_MINUTES.md:9`、`src/proxy.ts:11-15`
- **谁会踩到**：评审
- **会发生什么**：现有 Minit deck 讲社团会议／捐款；R1/R1c 则讲虚构的社区走道灯 request→resolution。后者页面又已经被移除。若 PDF、摘要、AI 声明来自不同套稿，评审会判断交件不可信或 artifact 不存在。
- **为什么会变成这样**：推测是比赛稿曾经转过题，但旧分支仍放在正式交件目录且没有 canonical／archive 标记；交件 checklist 也尚未授权发布。

### 04. 画面与 deck 把 pre-fill workbook 说成可直接上传 MyInvois 的正式 batch file
- **严重度**：🔴 挡住交件／上线
- **在哪**：`src/lib/einvois-xlsx.ts:11-17,43-58`、`src/app/money/einvois-pack.tsx:99-118`、`competition/summary-onepager.md:26-40`、`competition/qa-drill.md:192-200`、`competition/deck/Minit-Pitch-Deck-CURRENT.pdf:第 7 页`

### 06. 开收据没有使用仓库里已设计的原子化、幂等机制；重试可重复，200 笔会产生数百次 DB 请求
- **严重度**：🔴 挡住真实钱上线
- **在哪**：`src/app/money/actions.ts:93-150,167-201`、`supabase/migrations/20260726000000_client_id_and_receipt_lock.sql:14-23,50-67`、`supabase/migrations/20260730000000_receipt_series.sql:117-246`、`supabase/migrations/20260824000000_receipt_no_past_9999.sql:2-7,40-176`
- **谁会踩到**：财政、总会、开发者
- **会发生什么**：当前 action 每笔 donation 一次 insert、每张 receipt 一次 backlink update，而且 donation insert 没写 `client_id`；网路掉线后重按无法幂等。200 笔约 400 多次 DB round-trip，还可能留下需要人工 reconciliation 的半成品。migration 已经写出 advisory lock＋单 transaction 的 `issue_receipts()`，但 `src/` 没有 caller；其套用状态也没有一致证据。
- **为什么会变成这样**：新数据库设计写在 migration，应用层仍停在旧的 compensating rollback 版本；schema rollout 由人手操作，使「先接代码还是先跑 migration」长期悬空。

### 07. 公开注册要求同意一份页面自己写着「Do not publish」的法律文件

- **在哪**：`src/app/login/page.tsx:341-385`、`src/app/legal/legal-document.tsx:11-18`、`src/legal/documents.ts:14,80-115,224-241,303-365,373-491`
- **谁会踩到**：新使用者、资料主体、评审
- **会发生什么**：terms／privacy 有公司名、注册号、地址、email、保留期、跨境处理依据等大量 `[[ ]]`；privacy 原文明确说不可发布，却已是 public signup 的同意对象。实际打开 `/privacy` 还会看到 raw `**` 与占位符。
- **为什么会变成这样**：为了让 signup 有 consent link，先把「文件存在」当成「文件可生效」；缺的是 owner/legal gate，不是 Markdown renderer 一项小 bug。

## 排序结论

这不是「先把 UI 再磨漂亮」的阶段。真正的系统顺序是：**先阻止资料串组织与钱的重复／半成功，再补可恢复的核心闭环，然后才整理大量资料 UI；slide 最后改。** 目前是 **No-Go for real data**；不是 No-Go for the codebase。核心技术方向值得保留，也不需要重写。
