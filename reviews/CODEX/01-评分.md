# CODEX 外部评审：评分

评审日期：2026-08-24。**本版以系统是否真的能给社团使用为主，deck／submission 只当次要风险。** 分数按今天的代码、资料流、可恢复性和真实验证状态评，不按计划或未来承诺加分。

## 先讲系统结论

**系统不是该重做，而是还没到能放真实社团资料的阶段。** 底层方向与不少单元能力已经做对；当前挡住使用的四件事是：

1. browser working copy 没按帐号／组织隔离；
2. 正式收据流程不是单 transaction，也不能安全重试；
3. 会议等核心工作没有可靠的 server draft／resume；
4. MyInvois、WhatsApp、删除资料等画面承诺与系统实际行为不同。

这四项比 slide、美术或再加功能重要。

### 现在交，会不会进 2026 年 9 月初赛？

**只看今天系统完成度，我的判断仍是偏低，主观概率约 30%。** 不是因为 slide 不够漂亮，而是评审若实际操作，会遇到：核心能力无真实手写验证、核心 route 无公开可用流程、MyInvois 交付边界不实、钱与组织资料的安全闭环未完成。deck 冲突可以在数小时内修，以上系统问题不能靠换文案解决。

如果在截止前把一条核心系统流程修到可安全操作，再把该流程如实呈现，判断可以改变；继续补 glossary、AGM、日历等外围功能不会改变。

### 最伤的一句评审问题

> **「我现在能把 Minit 下载的这个 `.xlsx` 原样上传 MyInvois 吗？为什么 deck／画面说可以，但 `src/lib/einvois-xlsx.ts:11-15,47-50` 明写它只是 pre-fill pack，还要再复制进官方 11-sheet template？」**

这不是「尚未优化」，而是核心价值与实际交付物相反。答错会伤诚信；诚实回答则会暴露 slide 所示闭环尚未完成。

### 先救谁

**最低是 C，先救 C 的核心任务流。** 但不是先做一个「老人版皮肤」；先把英雄流程改成：预设单一语言、一个画面只问一个决定、每一步明确显示「已保存／还没保存」、允许退出后继续、危险动作有可撤销或明确补救。这个改法同时会救 B，也会让比赛 demo 变得可理解。

安全顺序另算：在任何真人捐款资料进入系统前，必须先修跨帐号／跨组织 localStorage 隔离；再漂亮的老人流程也不能盖过资料外泄。
